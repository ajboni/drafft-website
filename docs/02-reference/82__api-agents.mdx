# Using the API as an Agent

This page is written as instructions, not reference tables. For fields and schemas, use the [full API reference](/docs/reference/api) and the OpenAPI document at `/v1/openapi.json`.

## Before you start

- The app must be running and a project must be open.
- Base URL: `http://127.0.0.1:9001`
- Authentication: send the API key as `x-api-key`, or as `Authorization: Bearer <key>`.
- Reads use the read key. Writes need the separate write key, and `Enable Write API` must be on. A read key cannot write.
- Check readiness first:

```rest
GET /v1/ready
```

If `dbLoaded` is false, ask the user to open a project. If `searchReady` is false, wait before searching. If `writesReady` is false, wait or ask the user to enable the write API.

## First calls

```rest
GET /v1/info
GET /v1/collections
```

`/v1/info` gives the project name, description, app version, and capabilities. `/v1/collections` gives the document types and counts.

Use the **singular collection names** returned by `/v1/collections` (`Dialogue`, `Script`, `Gdd`, `Actor`, …), not the plural export-section names used by `/game-export`.

## Lists are summaries

Collection lists return a small summary by default. Only request bodies when you need them:

```rest
GET /v1/collections/Dialogue/documents?limit=20
GET /v1/collections/Dialogue/documents?limit=20&include=content
GET /v1/collections/Dialogue/documents?limit=20&fields=*
```

Use `limit` + `offset` and follow `nextOffset` while `hasMore` is true. Do not request `limit=9999`; the API caps lists at 500.

## Create a document

```rest
POST /v1/documents
x-api-key: <write-key>
content-type: application/json

{
  "name": "New dialogue",
  "type": "Dialogue"
}
```

- `type` and `name` are required.
- `collection` defaults to `type`. For a `Folder`, pass the section it belongs to, for example `"collection": "Script"`.
- `parentId` must be a `Folder` in the same collection.
- `id` is optional and must match `^[A-Za-z0-9_-]{1,128}$`. Omit it to let Drafft generate one.
- `content` is merged into the default content; `props` is for type-specific options such as a Kanban template.
- The response is `201` with the new document, including `_rev` and `path`.

The `POST` endpoint is create-only. Reusing an existing id returns `409 id_exists`. Do not create `ProjectSettings`, `User`, `Attachment`, `DialogueFolder`, or other internal documents.

### Variables are sets

A `Variable` document is a **variable set**, not a scalar. The root variable name is `content.json._sid`; the document name and id are only labels.

Example: a document named `Player` with `_sid: player` and a `style` field:

```json
{
  "name": "Player",
  "type": "Variable",
  "content": {
    "variables": "_sid: player\nstyle: A",
    "json": "{\"_sid\":\"player\",\"style\":\"A\"}"
  }
}
```

Scripts use `variables.player.style`, not the document name or id. Keep `content.variables` and `content.json` consistent, and do not change `_sid` once scripts reference it.

### Document formats are client-side

For `Item`, `Actor`, `Quest`, and `Misc` documents, `editorLanguage` tells Drafft how to interpret the text (`hjson`, `json`, `toml`, `yaml`, or `text`). The API stores that text as-is.

The API does not convert formats or infer a structure from plain text. If you convert a document, parse the current format yourself, rewrite `content`, then update `editorLanguage` and `content` together. Changing only `editorLanguage` leaves the old text in the new format label.

### Runtime state

- **Variable updates** refresh live variable defaults through the same state-store path as the Variable editor.
- **Scenario updates** change the stored scenario only. They do not activate it or replace live state. Loading a scenario remains an explicit action.
- The API has no live-scenario activation/reset endpoint and no direct live-variable write endpoint.

## Import a bundle

Export the source documents with dependencies:

```rest
GET /v1/documents/<dialogueId>/bundle?dependencies=true
```

A bundle is `{ "rows": [{ "id", "doc" }] }`. Bundles keep `_rev`; locks, revision history, attachments, and dialogue runtime layout are stripped. Use `stripRev=true` only for templates.

Validate before writing:

```rest
POST /v1/documents/import?dryRun=true
content-type: application/json

{ "rows": [ ... ] }
```

Then run the same request without `dryRun`:

```rest
POST /v1/documents/import
```

- `mode=create` adds documents. `mode=update` requires existing documents and matching `_rev`. `mode=upsert` creates missing documents and updates existing ones.
- `revPolicy=current` lets an existing document without `_rev` use its current revision. A supplied stale `_rev` is still a conflict.
- `parent` is authoritative. Import recomputes `path` and `children`; do not trust exported paths.
- Every parent must exist and be a `Folder` in the same collection. A Dialogue’s `dialogueScriptFolderID` must also resolve to a Folder. Missing parents or folders, cycles, duplicate ids, and type/collection mismatches return `400 validation_failed`.
- Updating a document requires a free document: no unsaved semantic tab edits and no lock. Otherwise the import returns `409 dirty_buffer` or `423 locked`.
- Existing ids are conflicts in `create` mode. Stale or missing revisions are conflicts in `update`/`upsert`. Dry-run returns `200` with `valid: false`; a real import returns `409 import_conflict`.
- Dry-run does not write. A real import reports per-document actions and a summary such as `4 updated, 1 created`.
- Created documents are rolled back best-effort if a write fails. Updates already applied are not rolled back. The import is not a database transaction.
- Import does not support `_attachments`; use a project backup/restore for binary attachments.

## Edit one document's content

For a targeted edit, use `PATCH` instead of a one-row bundle:

```rest
GET /v1/documents/<id>
PATCH /v1/documents/<id>
x-api-key: <write-key>
content-type: application/json

{
  "rev": "<current rev>",
  "content": { "script": "...full updated script..." }
}
```

`PATCH` is content-only and currently supports `Script` (`content.script`) and `Gdd` (`content.gdd`). It replaces the entire content object. It does not rename, reparent, delete, or lock.

Rules:

- Always re-read before editing and send the current `rev`.
- Missing `rev` → `428 rev_required`.
- Stale `rev` → `409 stale_rev` with `currentRev`; re-read and reapply.
- Open tab with unsaved semantic edits → `409 dirty_buffer`; ask the user to save or discard.
- Locked document → `423 locked`; ask the user to unlock or close it.
- A clean, unlocked open tab is allowed and refreshed.
- Use `?dryRun=true` to validate without writing.

Success returns the document and a nudge. Reuse the returned `_rev`; never retry an edit with the old revision.

## Story questions

Read the GDD first. It usually answers “what is the story?” in one call:

```rest
GET /v1/collections/Gdd/documents?include=content
```

Then use dialogues, scripts, and actors only to confirm details.

## Scene and dialogue questions

Start with node search, not document search:

```rest
GET /v1/search?q=forest&scope=nodes&limit=10
```

Node results include `dialogueId`, `dialogueName`, `nodeId`, `label`, `scriptId`, and `route`.

Then read the dialogue with its scripts:

```rest
GET /v1/documents/<dialogueId>/nodes?include=script
```

The response contains:

- `items[].handles` — ports with `label`, `type`, `portScript`, and condition/switch flags
- `items[].script` — the script document when `include=script` is used
- `edges` — `source`/`sourceHandle` → `target`/`targetHandle`

Follow `edges` to go from a node to its next node. Do not fetch the whole Script collection to find one dialogue’s scripts.

## Choice questions

A choice node’s options are its **source handles**. Each source handle may have a `portScript` that runs when that port is followed.

1. Read the choice node’s `handles` where `type` is `source`.
2. Find the edge whose `source` is the choice node and whose `sourceHandle` matches the handle.
3. Read the `target` node’s `scriptId` (or its `script` when `include=script` is used).
4. Read the target script to see the actual consequences.

If several handles point to the same target, the consequences are usually branched inside that target script.

## Where is this used?

```rest
GET /v1/documents/<id>/references?direction=incoming|outgoing|both
```

This is computed on demand from current project data. There is no secondary index to get out of sync.

Use `kind` to interpret the result:

- `dialogue-owner` — the dialogue that owns a script through its script folder (`ownedBy`)
- `dialogue-node-script` — nodes that link to a script through `scriptId` (`linkedBy`)
- `dialogue-script-folder` — a dialogue’s script folder
- `scene-item` — a scene’s playlist item
- `gdd-link` — a GDD `:doc{#id}` link
- `related` — a dialogue node’s related document

A script can be **owned by one dialogue** and **linked by many nodes**. Do not assume a one-to-one parent/child relationship.

## Search scopes

- `scope=documents` — default; document-level results, fuzzy/prefix
- `scope=nodes` — dialogue nodes only; best for events, labels, and lines
- `scope=all` — both; useful but can be noisy for short names

Node results use `type: "DialogueNode"` and `collection: "Dialogue"`.

## Do not

- Do not use `/db-dump` for normal reads. It is a backup endpoint and compacts the database.
- Do not attempt rename, reparent, or delete through the content `PATCH` endpoint. It only changes content.
- Do not edit a document with unsaved tab changes or a lock; the API will reject it.
- Do not import `ProjectSettings`, `User`, `_local/*`, `Attachment`, `DialogueFolder`, or other internal documents.
- Do not assume `capabilities.write` means a write will succeed. Check `writesReady`, use the write key, and prefer `dryRun=true` before importing into a real project.

## Errors

v1 errors use:

```json
{
  "error": {
    "code": "not_found",
    "message": "Document not found: abc123",
    "reason": null,
    "details": null
  }
}
```

Common statuses:

- `400` — malformed request or bundle validation failure
- `401` — missing or invalid read key
- `403` — write API disabled or write key required
- `404` — document or route not found
- `409` — existing id, stale revision, dirty tab, or import conflict
- `423` — document is locked
- `425` — project or search index not ready
- `428` — required `rev` is missing
- `500` — unexpected error

Legacy endpoints use the older `{ "error": "..." }` shape.

## Worked examples

### Summarize the story

```bash
curl -H "x-api-key: $KEY" \
  "http://127.0.0.1:9001/v1/collections/Gdd/documents?include=content"
```

### Find a scene and read its scripts

```bash
curl -H "x-api-key: $KEY" \
  "http://127.0.0.1:9001/v1/search?q=forest&scope=nodes&limit=10"

curl -H "x-api-key: $KEY" \
  "http://127.0.0.1:9001/v1/documents/<dialogueId>/nodes?include=script"
```

### Find where a script is used

```bash
curl -H "x-api-key: $KEY" \
  "http://127.0.0.1:9001/v1/documents/<scriptId>/references?direction=both"
```

### Open a dialogue focused on a node

```bash
curl -H "x-api-key: $KEY" \
  "http://127.0.0.1:9001/navigate?id=<dialogueId>&nodeId=<nodeId>"
```

Add `&scriptId=<scriptId>` to open the node’s script subtab explicitly.

### Create a script

```bash
curl -X POST "http://127.0.0.1:9001/v1/documents" \
  -H "x-api-key: $WRITE_KEY" \
  -H "content-type: application/json" \
  -d '{"name":"Imported scene","type":"Script"}'
```

### Import a bundle safely

```bash
curl -X POST "http://127.0.0.1:9001/v1/documents/import?dryRun=true" \
  -H "x-api-key: $WRITE_KEY" \
  -H "content-type: application/json" \
  --data-binary @bundle.json

curl -X POST "http://127.0.0.1:9001/v1/documents/import" \
  -H "x-api-key: $WRITE_KEY" \
  -H "content-type: application/json" \
  --data-binary @bundle.json
```

### Edit a script

```bash
curl -X PATCH "http://127.0.0.1:9001/v1/documents/<scriptId>" \
  -H "x-api-key: $WRITE_KEY" \
  -H "content-type: application/json" \
  -d '{"rev":"<current rev>","content":{"script":"::Kenji:: New line.\n"}}'
```

Re-read the document after the response and use the returned `_rev` for the next edit.
